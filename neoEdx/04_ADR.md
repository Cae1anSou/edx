# NeoEdx 架构决策记录（ADR）

> 本文档记录 NeoEdx 项目中的关键架构决策及其背后的考量。

---

## ADR-001：采用领域驱动设计（DDD）架构风格

### 上下文

在分析 Open edX 后，我们发现其 Django 单体架构存在以下问题：
- 业务逻辑分散在多个 Django App 中
- 领域边界不清晰，导致循环依赖
- 测试和维护困难
- 难以独立扩展特定功能

### 决策

采用领域驱动设计（DDD）作为核心架构风格，将系统划分为多个有边界的领域上下文，每个领域拥有自己的数据、行为和对外接口。

### 方案对比

| 方案 | 优点 | 缺点 |
|------|------|------|
| 领域驱动设计（DDD） | 边界清晰、业务聚焦、可独立演进 | 学习曲线、复杂度较高 |
| 微服务架构 | 独立部署、技术多样 | 分布式复杂度、运维成本高 |
| 模块化单体 | 简单直接、易于开发 | 边界难以维护、扩展受限 |
| 垂直切分 | 按业务线划分、团队独立 | 重复建设、共享逻辑难处理 |

### 决策理由

1. **业务复杂度匹配**：LMS 业务逻辑复杂，DDD 能很好捕捉领域概念
2. **渐进式演进**：可以从单体逐步拆分为分布式系统
3. **团队协作**：清晰的边界支持多团队并行开发
4. **技术灵活性**：每个领域可以选择最适合的技术栈

###  Consequences

**正面影响**
- 业务代码组织更清晰
- 领域边界明确，减少循环依赖
- 便于测试和重构
- 支持渐进式架构演进

**负面影响**
- 初始开发复杂度增加
- 需要团队具备 DDD 知识
- 跨领域协调需要额外机制

## ADR-002：采用事件驱动架构处理跨领域通信

### 上下文

领域之间需要通信（如成绩变更需要通知证书生成），同步调用会导致：
- 紧耦合
- 性能瓶颈
- 容错困难

### 决策

采用事件驱动架构（EDA）作为领域间主要的通信方式，使用消息队列作为事件传输基础设施。

### 方案对比

| 方案 | 优点 | 缺点 |
|------|------|------|
| 事件驱动 | 解耦、异步、容错 | 复杂度、调试困难 |
| 同步调用 | 简单、可预测 | 紧耦合、性能瓶颈 |
| Saga模式 | 长事务支持 | 复杂、补偿逻辑 |
| 事件溯源 | 完整历史、可回溯 | 存储成本、复杂度 |

### 决策理由

1. **松耦合**：领域间通过事件交互，无需直接依赖
2. **可扩展性**：可以独立扩展生产者和消费者
3. **容错能力**：事件可以重试，失败不影响其他领域
4. **审计能力**：事件日志本身就是审计追踪

###  Consequences

**正面影响**
- 领域间完全解耦
- 支持异步处理
- 便于添加新消费者
- 天然支持审计

**负面影响**
- 调试和追踪困难
- 需要处理事件顺序和幂等
- 事件丢失需要补偿机制

## ADR-003：使用 REST API 作为服务间通信协议

### 上下文

服务间需要提供 API 供前端和内部服务调用，需要选择合适的通信协议。

### 决策

所有服务间 API 采用 RESTful 风格设计，使用 JSON 作为数据交换格式。

### 方案对比

| 方案 | 优点 | 缺点 |
|------|------|------|
| REST | 简单、广泛支持、缓存友好 | 大数据传输效率低 |
| GraphQL | 灵活查询、减少请求数 | 复杂度高、缓存困难 |
| gRPC | 高性能、强类型 | 需要特殊客户端 |
| WebSocket | 实时双向通信 | 状态管理复杂 |

### 决策理由

1. **简单性**：团队熟悉 REST，开发成本低
2. **工具链完善**：大量工具支持 API 文档、测试、监控
3. **缓存友好**：符合 HTTP 缓存语义
4. **语言无关**：任何语言都可以轻松调用

###  Consequences

**正面影响**
- 开发效率高
- 调试和测试方便
- 便于集成第三方系统
- 良好的缓存支持

**负面影响**
- 对于复杂查询可能需要多次请求
- 实时性支持不如 WebSocket

## ADR-004：采用读写分离的数据访问模式

### 上下文

系统需要支持大量的读操作（学习者浏览课程内容），以及相对较少但关键的写操作（提交作业、评分）。

### 决策

采用读写分离架构：
- 写操作走主数据库
- 读操作走从数据库（副本）

### 方案对比

| 方案 | 优点 | 缺点 |
|------|------|------|
| 读写分离 | 性能提升、主库减压 | 数据延迟、一致性 |
| CQRS | 灵活读写模型 | 复杂度高 |
| 单库处理 | 简单、一致 | 性能瓶颈 |
| 分库分表 | 水平扩展 | 跨库查询复杂 |

### 决策理由

1. **性能优化**：读操作可以充分利用从库资源
2. **主库减压**：减少主库压力，提高写入性能
3. **成本控制**：从库成本相对较低

###  Consequences

**正面影响**
- 读性能显著提升
- 主库压力降低
- 成本效益好

**负面影响**
- 存在主从延迟（通常秒级）
- 需要处理读写分离的异常情况

## ADR-005：使用 JWT 进行无状态认证

### 上下文

系统需要支持分布式部署，用户会话需要在多个服务间共享。

### 决策

采用 JWT（JSON Web Token）作为用户认证凭证，实现无状态认证。

### 方案对比

| 方案 | 优点 | 缺点 |
|------|------|------|
| JWT | 无状态、可扩展、跨域友好 | 令牌大小、难以撤销 |
| Session | 易理解、可控性强 | 需要共享存储、扩展困难 |
| OAuth2 Token | 标准化、授权灵活 | 复杂度高 |
| API Key | 简单直接 | 安全性有限 |

### 决策理由

1. **无状态**：不需要服务端存储会话，便于水平扩展
2. **自包含**：令牌包含用户信息，减少查询开销
3. **跨域友好**：适合微服务架构
4. **标准化**：广泛支持，工具成熟

###  Consequences

**正面影响**
- 服务可水平扩展
- 无需会话存储
- 跨服务认证简单

**负面影响**
- 令牌一旦签发难以撤销
- 令牌过大影响传输效率
- 需要额外的刷新机制

## ADR-006：采用策略模式处理成绩计算

### 上下文

不同课程可能有不同的评分策略（如按百分比、按等级、按达标线），需要灵活支持多种计算规则。

### 决策

采用策略模式设计成绩计算模块，定义统一的评分接口，允许不同课程使用不同的评分策略。

### 方案对比

| 方案 | 优点 | 缺点 |
|------|------|------|
| 策略模式 | 灵活、可扩展、符合开闭原则 | 类数量增加 |
| 条件分支 | 简单直接 | 违反开闭原则、维护困难 |
| 配置文件驱动 | 灵活、无需代码改动 | 功能受限、性能开销 |
| 规则引擎 | 强大灵活 | 学习成本、额外依赖 |

### 决策理由

1. **可扩展性**：新增评分策略不需要修改现有代码
2. **清晰性**：每种策略独立实现，逻辑清晰
3. **可测试性**：每个策略可以独立测试

###  Consequences

**正面影响**
- 易于添加新的评分规则
- 策略可以复用
- 代码易于维护

**负面影响**
- 需要良好的策略注册机制
- 策略间可能存在差异需要仔细设计接口

## ADR-007：使用内容快照确保成绩稳定性

### 上下文

课程内容可能会在学期中更新（如修改题目），但学生的成绩应该基于他们学习时的内容计算。

### 决策

在学生提交答案和计算成绩时，保存当时可见内容块的快照，后续成绩计算基于快照而非最新内容。

### 方案对比

| 方案 | 优点 | 缺点 |
|------|------|------|
| 内容快照 | 成绩稳定、可追溯 | 存储成本、复杂度 |
| 动态计算 | 无额外存储、始终最新 | 成绩可能变化 |
| 版本锁定 | 简单、确定 | 灵活性差 |

### 决策理由

1. **公平性**：学生基于学习时的内容被评估
2. **可追溯性**：可以重现历史成绩计算过程
3. **合规性**：满足教育机构对成绩稳定性的要求

###  Consequences

**正面影响**
- 成绩计算稳定可追溯
- 符合教育行业规范
- 便于成绩申诉处理

**负面影响**
- 增加存储成本
- 复杂度增加
- 需要管理快照生命周期

## ADR-008：采用异步任务处理长时间运行操作

### 上下文

某些操作如证书生成、批量注册、邮件发送等耗时较长，不应同步阻塞用户请求。

### 决策

将长时间运行的操作放入异步任务队列处理，通过事件驱动触发任务执行。

### 方案对比

| 方案 | 优点 | 缺点 |
|------|------|------|
| 异步任务 | 用户体验好、可扩展 | 复杂度、状态管理 |
| 同步处理 | 简单、结果确定 | 用户等待、可能超时 |
| WebSocket推送 | 实时反馈 | 复杂度、状态管理 |
| 定时任务 | 批处理、简单 | 实时性差 |

### 决策理由

1. **用户体验**：用户无需等待长时间操作
2. **可扩展性**：可以独立扩展任务处理能力
3. **可靠性**：任务可以重试，保证最终一致性

###  Consequences

**正面影响**
- 提升用户体验
- 提高系统吞吐量
- 便于故障恢复

**负面影响**
- 增加系统复杂度
- 需要任务状态管理
- 调试和监控更复杂

## ADR-009：采用微前端架构支持前端独立部署

### 上下文

Open edX 的前端是一个庞大的单体，影响开发效率和部署灵活性。

### 决策

采用微前端架构，将前端拆分为多个独立应用（LMS、Studio、Dashboard 等），支持独立开发、测试和部署。

### 方案对比

| 方案 | 优点 | 缺点 |
|------|------|------|
| 微前端 | 独立部署、技术多样、团队独立 | 集成复杂度、共享依赖 |
| 单体前端 | 简单、共享依赖 | 部署耦合、团队协作 |
| 模块化单体 | 折中方案 | 边界维护困难 |
| 组件库共享 | 复用、一致 | 版本管理复杂 |

### 决策理由

1. **团队独立**：不同团队可以独立开发自己的前端
2. **技术灵活**：每个前端可以选择最适合的技术栈
3. **快速部署**：修改可以快速部署，不影响其他部分
4. **渐进升级**：可以逐步迁移旧代码

###  Consequences

**正面影响**
- 开发效率提升
- 部署更灵活
- 技术栈可演进

**负面影响**
- 集成复杂度增加
- 共享状态和样式需要管理
- 开发工具链更复杂

## ADR-010：使用服务发现实现动态服务寻址

### 上下文

微服务架构中，服务实例数量和位置会动态变化（扩容、缩容、故障转移）。

### 决策

采用服务发现机制（如 Consul、Eureka 或 Kubernetes Service），服务启动时注册，停止时注销，客户端通过服务名动态获取服务地址。

### 方案对比

| 方案 | 优点 | 缺点 |
|------|------|------|
| 服务发现 | 动态、高可用 | 复杂度、额外依赖 |
| 静态配置 | 简单直接 | 不灵活、运维负担 |
| DNS发现 | 简单、标准 | 功能有限、延迟高 |
| API网关 | 统一入口、简化调用 | 单点风险、额外延迟 |

### 决策理由

1. **动态性**：自动适应服务实例变化
2. **高可用**：自动绕过故障实例
3. **弹性**：支持自动扩缩容

###  Consequences

**正面影响**
- 运维自动化程度高
- 系统弹性好
- 便于滚动升级

**负面影响**
- 增加系统复杂度
- 需要服务发现基础设施
- 调试更复杂

## ADR-011：采用统一的错误处理和响应格式

### 上下文

多个服务需要有统一的错误处理机制和 API 响应格式，便于前端处理和调试。

### 决策

定义统一的 API 响应格式和错误代码规范，所有服务遵循统一模式。

### 标准响应格式

**成功响应**
```json
{
  "success": true,
  "data": { ... },
  "meta": {
    "timestamp": "2024-01-01T00:00:00Z",
    "request_id": "uuid"
  }
}
```

**错误响应**
```json
{
  "success": false,
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "邮箱格式不正确",
    "details": [...]
  },
  "meta": {
    "timestamp": "2024-01-01T00:00:00Z",
    "request_id": "uuid"
  }
}
```

### 决策理由

1. **一致性**：前端可以统一处理所有响应
2. **可调试性**：统一的错误码便于问题定位
3. **可追溯性**：request_id 支持请求追踪

###  Consequences

**正面影响**
- 开发效率提升
- 用户体验一致
- 便于监控和分析

**负面影响**
- 需要团队严格遵守规范
- 错误码设计需要全面考虑

## ADR-012：采用 PostgreSQL 作为主数据库

### 上下文

系统需要选择可靠、可扩展的关系型数据库存储核心业务数据。

### 决策

采用 PostgreSQL 作为主数据库，理由如下：

### 方案对比

| 方案 | 优点 | 缺点 |
|------|------|------|
| PostgreSQL | 开源、功能强大、扩展性好、社区活跃 | 复杂查询优化需要经验 |
| MySQL | 成熟稳定、生态完善 | JSON支持较弱、GIS功能有限 |
| MariaDB | 完全兼容MySQL、性能优化 | 生态相对较小 |
| Oracle | 企业级支持、功能完善 | 授权成本高 |

### 决策理由

1. **JSON支持**：PostgreSQL 原生支持 JSONB 类型，适合存储灵活的结构化数据（如内容块数据）
2. **扩展性**：支持丰富的扩展（如 PostGIS、pg_cron），生态完善
3. **可靠性**：成熟的事务处理、MVCC 机制
4. **社区**：活跃的开源社区，大量最佳实践

###  Consequences

**正面影响**
- 强大的数据完整性保证
- 灵活的 schema 设计支持
- 丰富的索引类型和查询优化
- 良好的社区支持

**负面影响**
- 写入性能在高并发场景下可能需要优化
- 需要 DBA 专业知识进行调优

## ADR-013：采用多级缓存策略

### 上下文

系统需要优化访问性能，减少数据库压力，降低响应延迟。

### 决策

采用多级缓存架构：
- **L1**：应用本地缓存（如 Guava Cache）
- **L2**：分布式缓存（Redis Cluster）
- **CDN**：静态资源缓存

### 方案对比

| 方案 | 优点 | 缺点 |
|------|------|------|
| 多级缓存 | 性能最优、容错性好 | 复杂度高、一致性挑战 |
| 单级Redis | 简单、一致性好 | 性能有限、网络依赖 |
| 本地缓存 | 低延迟、无网络开销 | 扩展困难、内存限制 |
| 不使用缓存 | 简单、数据一致 | 性能差、数据库压力大 |

### 决策理由

1. **性能最优**：热点数据在本地缓存，延迟最低
2. **容错性**：Redis 故障时本地缓存仍可服务
3. **成本控制**：减少数据库查询，降低资源消耗

###  Consequences

**正面影响**
- 显著降低响应延迟
- 减少数据库负载
- 提高系统吞吐量

**负面影响**
- 缓存一致性需要额外处理
- 缓存失效逻辑复杂
- 需要监控和调优

## ADR-014：采用渐进式数据迁移策略

### 上下文

从 Open edX 迁移数据到 NeoEdx，数据模型可能变化，需要安全的迁移策略。

### 决策

采用渐进式双写策略：
1. 新系统写入时同步写入新旧系统
2. 逐步迁移历史数据
3. 验证数据一致性
4. 切换读流量
5. 停止旧系统写入

### 方案对比

| 方案 | 优点 | 缺点 |
|------|------|------|
| 渐进式迁移 | 安全、可回滚 | 周期长、复杂度高 |
| 一次性迁移 | 快速、简单 | 风险高、回滚难 |
| 蓝绿部署 | 切换快、回滚快 | 资源双倍 |
| 并行运行 | 充分验证 | 成本高、数据同步 |

### 决策理由

1. **风险可控**：可以逐步验证，发现问题及时回滚
2. **业务连续**：不影响现有业务
3. **数据完整性**：确保数据不丢失

###  Consequences

**正面影响**
- 迁移风险低
- 可验证数据正确性
- 支持回滚

**负面影响**
- 迁移周期长
- 需要维护双写逻辑
- 成本较高
